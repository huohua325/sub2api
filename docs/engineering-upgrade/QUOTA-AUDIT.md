# 学员额度与重置倒计时审查

后续规则澄清：用户已明确个人周期独立于母账号、Codex 默认50点、Grok 默认30点，并要求处理 Codex 全体异常重置。下文记录审查时的实际旧行为，改造方向见 [QUOTA-REDESIGN.md](QUOTA-REDESIGN.md)。

日期：2026-10-27，时间示例统一使用北京时间。前端设计提交为 `7498ba6be`。审查对象是提交后的实际工作区，包含原有尚未提交的 `user_handler.go`、`official_point_service.go` 改动；不是只审查该 commit 的差异。

结论：**分摊公式按当前定义能够成立，默认实验月度换期也正确，但“展示、拦截、重置”没有完全使用同一口径，不能认定整体正确。** 本次只提交此前设计工作并分析算法，没有调整计费、权限、数据库或额度规则。

## 当前如何计算

### Codex 与 Grok Build

以每个母账号的当前官方窗口为单位，定义：

- `Pj`：该母账号官方已用百分比，1 个百分点记为 1 点。
- `Uij`：当前用户在这个母账号、这个官方窗口内的网关 `actual_cost`。
- `Sj`：所有用户在同一母账号、同一官方窗口内的网关 `actual_cost` 合计。
- `B`：每人、每用途上限，默认 Codex 50 点，Grok 80 点；可由后台设置改变。

```text
单个母账号分摊点数 = round4(Uij / Sj × Pj)
用户该用途已用点数 Q = 同平台各可读母账号分摊点数之和
显示百分比 = min(100, round_half_up(Q / B × 100))
后端点数拦截 = Q >= B
```

两个平台分别计算，不把 Codex 与 Grok 的百分比相加。同平台多个母账号先分别分摊并舍入，再求和；不会给每个母账号重复发一份个人上限。实现使用 `math/big.Rat` 处理点数计算，避免普通浮点累加误差。

例：官方已用 40 点，全部网关费用 20，自己费用 5，则自己分到 10 点；Codex 上限 50 点时显示 20%。这并不表示母账号官方已用 20%。

Codex 官方统计区间是 `[官方 reset − 7天, 官方 reset)`；Grok 优先采用能与 `period_end` 对齐的 `period_start`，缺失或不合理时回退 7 天。统计还按母账号和重置戳匹配，重置时间允许 ±5 分钟漂移；生产 SQL 允许同母账号、同时间区间内缺少重置戳的记录加入。快照到期后不再参与计算；全部没有可读母账号时返回未知，点数闸门放行。部分母账号不可读时，目前只合计其余母账号，响应没有“部分缺失”标识。

`P` 存在而 `S<=0` 时，当前实现返回零点；这一点和 `backend/docs/official-point-percent.md` 中旧的 null 描述不同，但已有测试明确锁定零点行为，不能只凭旧文档判断应改成哪一种。

入口：[点数分摊](../../backend/internal/service/official_point_share.go)、[官方窗口与汇总](../../backend/internal/service/official_point_service.go)、[实际 SQL](../../backend/internal/repository/usage_monitor_repo.go)。

### API 实验

有效已用金额来自 `user_purpose_allowances`，默认上限 500 元、周期为北京时间自然月；后台可配置额度及 week/month 周期。

```text
默认当月有效已用 = 当前自然月账本 used_amount；旧窗口则视为 0
显示百分比 = min(100, round_half_up(有效已用 / limit_amount × 100))
后端用途拦截 = limit_amount >= 0 且 有效已用 >= limit_amount
```

对 `globalai.vip` 实验账户，费用取上游消费日志：按 `X-Oneapi-Request-Id` 匹配，`上游 quota / 500000 = 人民币金额`，覆盖本地模型价格与倍率结果。不是直接把模型页的展示价格相加。其他上游不能据此自动推断也采用人民币口径，需核对具体账单路径和部署配置。

默认月度边界正确：10 月 31 日 23:59:59.999999999 仍保留 10 月用量；11 月 1 日 00:00:00 有效用量为零，下一次重置为 12 月 1 日。查询时懒清零，下一笔入账时更新账本窗口；不要求定时任务在零点逐条改表。周周期按原始 `window_start` 的 7 天整数倍推进，长时间未使用也不会把周期重新锚定到访问当天。

入口：[窗口函数](../../backend/internal/service/purpose_allowance.go)、[实验实际费用](../../backend/internal/service/globalai_quota.go)、[入账](../../backend/internal/repository/usage_billing_repo.go)。

## 倒计时实际采用什么时钟

| 用途 | 当前返回的重置时钟 | 是否一定与当前已用数清零同步 |
| --- | --- | --- |
| Codex | 一个可读母账号即可采用官方 reset；多个母账号全部相差不超过 5 分钟时采用最早 reset，否则回退个人钱包时钟 | 单母账号通常一致；多母账号分散重置时不保证 |
| Grok Build | 至少两个可读母账号、且全部相差不超过 5 分钟，才采用共同官方 reset；否则采用个人钱包 7 天时钟 | **不保证，已复现不同步** |
| API 实验 | 用途钱包周期：默认下月 1 日北京时间零点，也支持配置为周 | 默认月周期一致；周配置的文字标签错误 |

所谓“个人注册周期”，实际上采用钱包 `window_start`。新注册初始化时取当时的时间，存量数据还可能来自旧平台周窗口迁移，不能保证始终精确等于 `users.created_at`。

前端以 `new Date(resets_at).getTime() - Date.now()` 计算剩余时间，每分钟更新一次。带 `Z` 或 `+08:00` 的 ISO 时间按同一瞬间解析，这部分没有把北京时间再错误地加一次 8 小时。超过一天时只显示天和小时；一天内显示小时和分钟，均向下取整；因此是分钟级展示，不是秒级准确计时。它依赖用户设备时钟，目前没有后端 `server_now` 校时。

入口：[时钟选择](../../backend/internal/service/official_quota.go:81)、[接口组装](../../backend/internal/handler/user_handler.go:119)、[学员倒计时](../../frontend/src/components/user/dashboard/StudentQuotaRuler.vue:177)。管理员另有 `rechargeCountdown`，可以区分已到期状态；学员卡没有复用该状态处理。

## 已确认的不一致

### 1. 高优先级：Grok 个人倒计时到点，并不会重置官方点数

`StudentCodingReset` 只替换返回给界面的时间，未改变 `pointsForUser` 统计的官方窗口，也未清掉其中的用户点数。后者没有读取个人钱包 `window_start`。

复现：个人周期从 10 月 20 日 10:00 开始，Grok 官方周期从 10 月 24 日至 10 月 31 日；在 10 月 27 日 10:00 前后，个人元钱包有效用量从 80 变为 0，倒计时终点从 10 月 27 日推进到 11 月 3 日，但官方已用仍为 **30.0000 点 → 30.0000 点**。若原来已经被点数闸门拦截，个人倒计时结束也不会因此恢复。

建议：先确定 Grok 应按官方周期还是个人周期清零。若采用官方周期，倒计时就应明确对应实际官方重置；多母账号只能说明“下一母账号窗口重置”，不能承诺总用量全部清零。若保留注册日起 7 天的个人额度，则需要真正的个人周期累计与结转设计；仅修改时间文案或 SQL 起点不能解决跨官方周期的点数可比性。

### 2. 高优先级：点数开关没有控制展示和拦截

`OfficialPointService.Enabled()` 能读取 `official_point_student_percent`，但当前展示、`Blocks`、`PurposeBlocks` 没有据此分支，服务也在 Wire 中无条件注入。

复现：`enabled=false`，Codex 用户点数超过 50，仍得到 `blocked=true, checked=true`。现有本地规格说关闭开关应回退元钱包，与实际代码不一致。

建议：决定该开关是否仍是有效产品功能；若保留，必须同时统一展示、鉴权和入账，不能只补一个 `Enabled()` 判断。当前结算只更新实验用途钱包，Codex/Grok 的旧元钱包不再正常累计，直接回退旧钱包也会不准确；若点数模式已永久启用，应移除或迁移无效开关与旧说明。

证据：[Blocks](../../backend/internal/service/official_point_service.go:157)、[PurposeBlocks](../../backend/internal/service/api_key_service.go:346)、[无条件注入](../../backend/cmd/server/wire_gen.go:265)。

### 3. 中优先级：显示 100% 被误当成真正耗尽

`49.8 / 50 × 100 = 99.6%`，四舍五入显示 100%；后端比较点数，`49.8 < 50`，所以放行。学员卡却以 `percent >= 100` 标记“已到上限，新的请求会被拒绝”。实验金额同样受四舍五入影响。

建议：接口返回独立的 `blocked`/额度状态，前端使用该状态控制耗尽文案，不从舍入后的百分比推断。百分比仍可保留现有舍入规则。管理员监控已有按实际点数比较上限的路径，学员与管理员当前可能给出不同状态。

证据：[真实阈值](../../backend/internal/service/official_point_share.go:62)、[学员状态判断](../../frontend/src/components/user/dashboard/StudentQuotaRuler.vue:97)。

### 4. 中优先级：倒计时过期和刷新失败会继续给出确定文案

学员倒计时把所有 `remaining <= 60000`，包括负数，都显示为“即将重置”。重置时间已过去 5 分钟仍是同一文案。额度刷新在已有成功数据时失败，只保留旧值，不设置失败或过期标识；两者叠加时可能长时间显示旧用量、“可以调用”或“即将重置”。

建议：区分正常倒计时、已到期等待确认、数据过期/刷新失败。刷新失败保留旧数值可以接受，但要显示观测/更新时间并取消确定性的可调用承诺；客户端倒计时结束不应自行宣布用量已经清零。恢复可见时立即更新本地时钟，并与后端时间校准。

证据：[负时间分支](../../frontend/src/components/user/dashboard/StudentQuotaRuler.vue:182)、[静默保留旧读数](../../frontend/src/composables/useStudentQuotas.ts:22)。

### 5. 中优先级：实验上限为零时，界面和后端含义相反

后台允许零上限。`used=0, limit=0` 时，后端用途判断为已耗尽并拒绝；百分比函数却按非正上限返回 0，学员卡于是显示 0%、“可以调用”。零额度需要明确展示为禁用/无额度，不能用百分比判断状态。

证据：[零上限实际拦截](../../backend/internal/service/api_key_service.go:374)、[零分母返回 0%](../../backend/internal/service/usage_monitor.go:916)。

### 6. 较低优先级：实验按周配置时仍标为自然月

后台 policy 允许 experiment 的 period 为 week；实际 `resets_at` 按该行 period 计算，但接口固定返回 `reset_scope="month"`。会出现“北京时间自然月”配合 7 天周期的错误说明。

建议：返回真实的 `period`/`reset_scope`，与重置计算共用定义。[接口位置](../../backend/internal/handler/user_handler.go:123)。

## 公式成立的限制

以下不是简单的算术错误，但决定它能否被当作硬额度账本：

1. **分摊值可下降。** 当 `U=10, P=40` 不变，其他用户使 `S` 从 20 增到 40，该用户点数会从 20 降到 10。快照滞后时尤其明显。这是动态按费用占比分摊的结果，不是可单调扣减的个人消费记录。
2. **网关费用权重不等于官方真实消耗。** 母账号存在网关外使用、用户倍率不同、模型官方消耗与本地价格不成比例时，不能称其为精确个人官方用量。点数是“网关观测分摊估算”。
3. **快照与费用可能不是同一观测时刻。** 当前 `P` 取保存的快照，费用汇总可能包含该快照之后的新记录。仪表盘刷新本身不会更新官方数据；缺失和过期快照采用放行策略，因此额度约束是软限制。
4. **实验上游账单缺失被记零。** GlobalAI 查询会做数次短重试，失败/没有匹配日志则清零本次费用；当前这条链路未发现后续补记。若要求精确结算，需要“待对账”状态及幂等补账，不能把失败和真实免费都当作最终零费用。这是现有代码的明确策略，并非本次修改。
5. **拦截是请求前检查，结算在请求后。** 没有针对该用途钱包的同额预留机制；并发请求、流式响应、异步结算和快照更新滞后都可能带来超额。不能据此承诺“一分不超”的硬限额。

## 验证记录

- 已有 Go 定向测试 12 项通过，涵盖分摊、同平台求和、真实点数阈值、官方窗口和个人/共享时钟选择。
- 审查补充实验 6 项通过：成功复现个人时钟与点数不同步、100% 未耗尽、他人用量使自己点数下降、开关无效、零上限状态矛盾，并验证默认北京时间月初换期。
- 另执行点数预算解析测试 1 项通过。
- GlobalAI 金额换算、请求 ID 匹配、日志解析、覆盖本地价格、编程用途不受影响、日志缺失记零等 6 项既有测试通过；均使用本地样例或 mock，没有向真实上游发送请求。
- 前端已有额度展示与仪表盘请求测试 4 项通过；审查补充实验 3 项成功复现 100% 错误耗尽文案、已过期仍提示即将重置、刷新失败无过期标记。
- 审查补充实验是对现有行为的复现，**测试通过不表示这些业务行为正确**。

审查用 Go 测试通过 `-overlay` 载入，前端临时测试运行后移除，没有给生产源码留补丁。复现源码和日志在被 git 忽略的 [output/quota-review](../../output/quota-review/)，既有测试日志在 `output/playwright/design-system/quota-*-existing.log`。没有读取生产数据库或调用真实上游账单，所以线上上限、实际母账号数量、快照新鲜度与费用单位仍需部署数据验证。

建议实施次序：先统一真实周期和额度状态契约，再处理开关、零额度、过期反馈，最后评估是否需要把估算分摊升级为可审计、可补账的个人额度账本。
