# MILE Lab 开发到部署流程效率调研

调研日期：2026-11-13（北京时间）。对象：`lab/0.2.17`，当前提交 `7331d642fb507261c0d6af2fa789af212c594dfe`。本次仅调研和记录，没有修改发布规则、应用代码、数据库或线上配置，没有重新运行上次的构建和测试。

## 结论

上次小修改耗时长，已能确认的原因包括：用户路径检查偏晚导致返工；验证入口重复；本地发布脚本没有固化；前端与 Go 程序绑定；公开网络验证遇到超时后临时排查；每次默认 PowerShell 调用都有额外启动开销。

不能把全部耗时归因于模型、上游限速或全量测试。现有记录没有模型推理、工具执行、人工等待的完整分段计时，也没有用户最初提出要求的时间。因此下列时间是已有证据覆盖的区间，不是精确的需求到交付总时长，各项节省也不能直接相加。

优先建议：先完善现有交付工具和验证顺序，再评估前端独立发布。第一阶段可以保留现有部署架构及额度保护要求。

### 2. 验证顺序造成返工

发布记录明确承认：前一轮 Base URL 检查只覆盖复制和布局，漏掉三个入口的真实导航，随后需要再次修复和发布。

本轮又在第一轮构建后发现重复锚点焦点和前进后退问题。测试失败日志包括 `repeat-focus-red.log`、`history-red.log`，证明这些是实际发现的问题，不是推测。

改进：小修改开始时先写清楚用户路径和可观察结果，先在运行页面验证核心交互。导航类修改的最小路径应包含入口、URL、可见目标、重复点击、后退/前进、深链接/刷新和键盘焦点。先完成针对性测试和浏览器快速复验，再进入最终完整验证及打包。生产构建后仍需验证实际产物，不能用开发模式结果替代。

### 3. 多个入口重复执行检查

`frontend/package.json` 的 `build` 已执行 `check:i18n`、`vue-tsc -b`、`vite build`；全量 Vitest 又包含 i18n 测试，外部流程还单独执行 `typecheck`。两轮构建的 i18n 检查分别用时 38.31、44.39 秒，实际断言只有 36、37 毫秒。

`localeKeyCompleteness.spec.ts` 使用 eager glob 载入所有 TS/Vue 原文，随后才过滤测试文件；因此过滤并不能避免测试文件在收集阶段被载入。最终一次收集阶段为 41.45 秒。这是可优化候选，但尚未做独立性能对照，不能承诺修改 glob 就能省掉全部时间。

改进：保留安全的常规 `build` 入口；交付编排记录每项检查对应的源码内容、依赖锁文件、配置、工具版本、命令和退出码，完全相同时复用结果。不同的类型检查命令不能未经核实就当作等价。评估在 glob 阶段排除测试原文，并保持生产源码和国际化检查覆盖范围。

源码或输入变化后，相关结果作废；不能只凭已有 `*.exit.txt=0` 放行新的提交。检查和构建可在同一内容快照上复用，但变更必须有可追溯的失效规则。

### 4. 发布脚本是一次性的，增加编写、审阅和修补成本

本次发布目录有 7 个 Python 辅助脚本，另有 `output/guide-navigation-20261111/package-release.py`。这些脚本不在 Git 的跟踪文件中。打包脚本固定了盘符、worktree、提交、上游 SHA、旧程序哈希和测试数量；服务器部署脚本还固定了迁移数量、历史事件 ID、某次对账摘要和特定用户的历史条件。

这些条件在当次发布有证据意义，但每次复制修改容易出错，也容易把历史事实错误地当成后续发布的永恒常量。

改进：把稳定逻辑移到受版本管理的 `tools/`，将每次发布的输入和核对结果放入 manifest。从实际状态发现数据库凭据、容器挂载、当前程序哈希和迁移集合；历史业务不变量与本次发布预期分开表达。`output/` 继续存证据和产物，不再承担唯一的工具源码职责。不能将密钥、容器完整环境或数据库快照提交到 Git。

已有可复用基础：`tools/serve_frontend_review.py`、`tools/review_mile_frontend.js`、`tools/review_connection_quota.cjs`，以及 `.github/workflows/release.yml` 的前端产物上传/复用机制。应扩展这些能力，避免再造整套发布平台。现有正式 Release workflow 主要面向 tag 和多目标发布，不能直接假定它就是单服务器小修改的最快路径。

### 5. 前端绑定整个 Go 程序，但这不是第一阶段必须改的架构

Vite 输出到 `backend/internal/web/dist`，`embed_on.go` 用 `go:embed` 打包。上次程序为 128,012,448 字节，gzip 后 39,928,952 字节；差量包只有 648,295 字节，生成差量用时约 66 秒。差量传输已经有效减少上传体积，不宜没有网络测量就换回每次上传完整程序。

当前 `data/public` 的 override 不能直接视为完整的前端热发布支持：首页模板在启动时从内嵌资源读取；是否存在文件也先查内嵌文件系统；新哈希资源不一定进入 override 分支。

前端独立发布值得作为第二阶段候选。优先评估让 Go 继续处理 HTML、公共配置注入和 CSP nonce，只将资源来源改为版本化前端目录，并提供原子切换及嵌入版本回退。还必须处理前端/后端协议兼容、旧页面引用的哈希资源保留、ETag、缓存失效和切换过程中的版本一致性。直接让 Caddy 静态托管全部页面会绕开现有注入逻辑，当前不能当作已经可用的捷径。

### 6. 发布后等待条件和网络故障处理不够固定

`browser-public.log` 明确显示：页面导航等待 `load` 超过 30 秒。后续改为页面可交互后验证，并完成了最终通过记录。资源核对脚本也是当次编写，超时和 TLS EOF 后又追加客户端/服务器对照。

改进：统一采用 DOM 就绪加明确业务元素就绪作为交互验证条件；页面确实依赖的资源仍应单独检查。将客户端网络、服务器到本机、服务器到公开 HTTPS 分开报告；仅对瞬时网络错误做有限重试。断言失败不能用重试掩盖，旧失败证据和最终结果都要保存。明确总超时预算，避免每个资源逐项使用很长超时导致整轮等待失控。

### 7. 默认 PowerShell 启动耗时可以直接减少

本次用同一条 `Write-Output 'shell-startup-probe'` 做了三组无副作用对照，均成功退出：

| 工具参数 | 三次执行耗时（秒） |
| --- | --- |
| 默认 `login=true` | 4.428、4.469、4.407 |
| `login=false` | 0.291、0.286、0.253 |

这是 shell 启动差异，尚未定位 profile 内部哪一项最慢。每次短命令约差 4.1 秒；若有 100 次这样的调用，算术上约 6.9 分钟，但上次实际调用数量与并行重叠未知，不能声称已经证实上次损失了 6.9 分钟。

后续普通命令直接使用 `login=false`，需要初始化环境的工具显式指定路径。继续使用 `D:/Programs/anaconda3/python.exe`；Windows 下优先用 `pnpm.cmd` 避开 PowerShell shim 的输出包装差异，前提是确认其路径可用。独立读取批量执行，搜索先限目录和文件类型，日志只回传摘要并保留原文件。本次已开始使用无 profile 的命令调用，没有修改用户 PowerShell 配置。

## 推荐的实施顺序

### 第一阶段：固化现有流程，保持部署架构

这是涉及验证、打包、部署和项目约定的中等规模工具改进，适合分步交付，不应与上游合并或前端架构调整捆绑。

1. 建立统一的分段计时与结果 manifest：记录开始/结束、源码和输入指纹、退出码、重试、产物哈希，输出简洁摘要。
2. 将已有 mock 浏览器脚本参数化，复用登录状态和接口 fixtures；对修改涉及的真实用户路径先做快速验证，再执行最终产物回归。
3. 固化本地验证入口，协调已有 lint/typecheck/i18n/测试/build，消除同一快照上的重复检查；适度并行 lint、测试及只读预检，避免高内存任务无限并行拖慢机器。
4. 固化单服务器发布工具：参数化打包、当前版本预检、校验传输、备份、原子替换、健康核对和程序回退；预检和工具准备尽量在停服前完成，必须保持一致性的账本核对仍走明确的一致性边界。
5. 发布后脚本自动生成文档所需数据；源码提交与后续发布记录提交保留各自含义，不为文档变更再构建程序。临时 worktree 清理放到交付关键路径之外，不处理用户已有残留。

建议用下一次低风险小改动校准：保留全量检查，比较各阶段时间和返工次数，再决定是否值得进一步缩小验证范围。15–25 分钟只作为热缓存、范围清晰的小修改的候选目标，当前不是实测承诺。

### 验证分级：需要先明确项目规则

| 变更类别 | 建议保留的重点 | 现有规则的约束 |
| --- | --- | --- |
| 文档、调研记录 | 链接、内容、diff 检查 | 无运行程序变化时不触发重新部署 |
| 展示/指南等前端修改 | 相关测试、受影响用户路径、lint、类型、i18n、一次最终构建和产物回归 | 按现有内嵌程序部署时，仍遵守升级的隔离 PostgreSQL 额度竞态和持久数据核对要求 |
| 登录/权限/密钥/用途配置界面 | 上述检查，加受影响权限、接口和拒绝路径；涉及额度输入则增加额度专项 | 不能只因文件在 frontend 就判为低风险 |
| 额度、计费、迁移、上游合并、运行配置 | 受影响后端检查、真实隔离数据库竞态、持久数据及运行配置核对，按 runbook 执行 | 不能以缺失 DSN 导致的 skip 作为通过；Codex/Grok 保持 shadow |

当前 `AGENTS.md` 写的是“额度相关改动及升级”都要执行真实数据库额度竞态，不能在本轮调研中自行解释成“纯前端部署可以跳过”。第一阶段先减少重复和返工即可提速。若以后要豁免某类发布，应单独提出准确条件、替代证据和失效条件，由用户明确决定后再修改约定。

### 第二阶段：评估前端独立发布

只有第一阶段计时表明 Go 编译、程序传输或重启已经成为主要瓶颈时，再实施。它需要独立的设计和兼容性验证；收益是 UI 修改不必每次编译和重启网关，代价是维护前后端版本组合、资源保留与回退规则。

不建议优先做：删除历史备份、降低额度保护、自动切 enforce、把每个任务都变成全平台发布、仅换模型来代替流程优化。

## 如何确认优化有效

建议至少记录三个实际的小修改交付样本，分别标明冷/热缓存及实际范围，观察：

- 从需求明确到线上验证完成的总时间；实现、检查、构建、传输、切换、公开验证和记录分别耗时多少。
- 最终源码快照的构建次数和复用次数；不同快照的必要重建应单独统计。
- 核心用户路径在全量检查前是否已通过；发布后补修次数。
- 必需检查是否实际执行，额度竞态是否零跳过，业务数据和 shadow 模式是否保持。
- 工具错误、网络重试和人工确认分别增加多少等待，而不是统一记为“Codex 慢”。
