# 个人额度计量与更新周期改造分析

日期：2026-10-27。依据用户在额度审查之后明确的新规则整理。本文保留原改造设计，工作区实现、验证结果及尚未实现的部分见 [QUOTA-IMPLEMENTATION.md](QUOTA-IMPLEMENTATION.md)。生产数据库尚未迁移。

## 已明确的业务规则

| 用途 | 每人默认上限 | 单位 | 默认更新周期 |
| --- | --- | --- | --- |
| Codex | 50 | 官方额度点 | 个人独立的 7 天 |
| Grok | 30 | 官方额度点 | 个人独立的 7 天 |
| API 实验 | 固定金额；当前默认 500 | 人民币元 | 1 个月；建议保留当前北京时间自然月 |

个人周期与母账号周期分开。母账号只是消耗计量来源：用哪个账号，就按该账号当时实际消耗的额度计算，再累计到用户自己的周期。多个母账号共享一份个人上限，不随账号数增加上限；同一个母账号服务多个用户时，分别计入各自账本。

Codex 存在全体账号非正常时间重置：确认此事件后，用户 Codex 额度也要重置。单账号普通换期、用重置卡、账号上下线、切换母账号，均不能直接等同于全体异常重置。当前只有一个账号，无法只凭这个账号的读数自动证明“全体”。

上述规则覆盖旧规格中 Codex/Grok 按母账号当前窗口重算个人用量、Grok 默认 80 点等约定。上一轮 [QUOTA-AUDIT.md](QUOTA-AUDIT.md) 记录的是旧实现现状。

## 当前实现为什么不能只修倒计时

`OfficialPointService.pointsForUser` 查询当前可读母账号，按每个账号当前官方窗口汇总费用，再计算 `个人费用 / 所有人费用 × 官方累计已用百分比`。它没有持久化独立的个人周期点数。

这会导致：

1. 个人 7 天到期，官方窗口还在，个人点数不会自然清零。
2. 母账号普通换期、快照不可读或账号被删除，个人展示/拦截可能丢掉此前消耗。
3. 其他用户消费、官方快照变化时，已经发生的个人消耗被重新分配。
4. `StudentCodingReset` 仅替换显示时钟，没有改变账本，且以账号 reset 时间接近判断 shared，不能证明发生过异常重置。
5. 现有点数上限与旧用途金额钱包各有配置，后者仍承载周期信息；继续拼接两者容易混用单位。

因此必须分离三件事：**母账号消耗计量、个人周期记账、特殊重置事件**。只把 SQL 起点改为个人周起点，也无法正确处理跨母账号窗口的消耗。

## 消耗算法：累计比例改为增量记账

### 点数含义

默认继续采用“母账号该官方额度窗口的一个百分点 = 1 点”。在 A 账号消耗 2 个百分点、B 账号消耗 3 个百分点，个人本期累计 5 点，Codex 上限仍是 50 点。

这可以兼容同类账号的多账户调度。不同套餐容量不同，其 1% 对应的实际算力也不同；如果将来要求不同套餐的算力等价，需另加标准容量换算规则。首轮不要悄悄改变点的定义。

### 数据来源优先级

1. 上游若提供可靠且可匹配请求的独立消耗，直接归属该请求；先核实协议能力，当前累计快照不能冒充请求级扣点。
2. 没有请求级消耗时，在同一母账号、同一计量窗口内，使用相邻可靠观察的消耗增量进行短区间分摊。
3. 官方读数延迟、舍入不变或缺失时，记录待结算；可用同账号/模型近期校准系数作暂估，但必须区分暂估与已结算，首批无样本不能声称精确或永久记零。

区间分摊的目标公式：

```text
区间总消耗 ΔP = P(t1) - P(t0)                 # 仅限同一官方计量窗口
请求 r 分摊点数 = ΔP × w(r) / Σw(该区间所有相关请求)
用户本期已用 = Σ归属该用户本周期的已结算点数 + 暂估点数
```

例如账号在一个可归属区间内由 20% 增至 26%，两个用户请求的计量权重为 1:2，分别累计 2 点和 4 点。下一区间的用户请求不会重新稀释已经结算的这 6 点。

`w(r)` 使用反映模型、输入输出、缓存等消耗的标准权重，不能使用含个人优惠/分组倍率的最终 `actual_cost`。同样的请求不应因为用户倍率不同而分到不同官方消耗。若以标准模型成本作权重，应保存当时的计价版本。

### 必须处理的计量边界

- 多人并发时，累计读数不能直接当成最后一个完成请求的扣点。按账号组织不重叠的结算区间，保存待归属请求；观察时间、请求开始/完成时间和后台落库时间分别记录。
- 响应头可能在生成完成前读取，Grok 账单也可能异步更新，不能机械地将“该时间区间完成的请求”视为全部消耗来源。需要验证各协议的延迟和读数语义；有跨界未完成请求时保留待结算，不能假装精确归属。
- 相同缓存读数只算一个观察；读数未变化也不等于请求免费。低精度读数需要累积足够样本，后续对账。
- 官方窗口更换时关闭旧计量段、建立新基线，禁止跨重置做 `P1-P0`，也不能简单把负差截为零而漏掉旧窗口尾部消耗。
- 乱序、重复、回退读数先验证其来源和观察时间；只回退百分比不能直接触发用户重置。
- 同一官方额度池里的影子账号、协议别名必须归并到真实母账号与正确额度桶；Codex 5h/7d、Spark/额外额度桶不得混算。相同上游凭证重复导入也需要识别，避免重复计算。
- 如果该官方池混有实验请求、管理员探测等流量，应参与实际消耗归属，再按请求发生时的用途记账；不能把整个池的增量都扣给 coding 用户。用途不能靠后来修改过的分组字段重算历史。
- 账号存在站外消耗时，单靠累计读数无法精确识别个人份额，应提示计量不完整/记录未归属差额；不能保证网关内用户承担的全部增量都是他们造成的。
- 点数使用十进制定点数持久化，展示再舍入。区间分摊的尾差采用确定性规则分配，保证本区间分配总和等于可归属消耗，不对每个微小请求独立舍入后丢失点数。

已有 `usage_monitor.go` 的 `slopeShare`、`usage_monitor_repo.go` 的观察时间及斜率查询可以参考，但它们目前是展示分析：会筛选更低的历史 P，且使用费用权重，不能直接当作幂等结算器。

## 个人账本与时间算法

### 普通周期

建议周周期沿用用户额度开通时的持久化锚点，已有用户迁移时明确映射其有效 `window_start`，不在部署或页面刷新时重新开始计时。

```text
W = 168 小时
k = floor((server_now - anchor) / W)
period_start = anchor + k × W
period_end   = period_start + W
```

使用左闭右开窗口 `[period_start, period_end)`，用户长期未访问时也跳到正确周期。后台读账、实际拦截、入账与前端倒计时全部使用同一个周期解析器。

建议每个实际发出的上游请求在发送前绑定个人 `period_id` 和用途；跨周期完成、晚到回执、重试补账仍写回原周期，不污染新周期。会话可能持续多天，不能将整个聊天会话永久绑定第一次请求所在周。若失败尝试已经消耗上游额度，应保留该尝试的计量，不能只记最终成功尝试。

按请求开始时归属周期是建议口径：上游累计快照不能严格拆出生成过程每一毫秒的消耗，跨周期区间中仍需保留相关请求并分摊到它们各自已绑定的个人周期。

API 实验建议保留 `[北京时间本月1日00:00, 下月1日00:00)`。这与“从每人开通日起满一个月”不同；用户本轮尚未明确改变现有自然月口径。

### Codex 全体异常重置

不能沿用 `SharedOfficialReset` 的“当前若干 reset_at 接近”算法。它没有重置前后证据，且排除了不可读账号，无法判断整个账号池。

需要持久化平台/额度池级重置事件，区分：

| 情况 | 母账号计量处理 | 个人额度处理 |
| --- | --- | --- |
| 单账号正常周换期 | 切换该账号计量窗口 | 保留个人累计与周期 |
| 单账号用重置卡 | 切换该账号计量窗口 | 保留个人累计与周期 |
| 换账号、上下线、新增/删除账号 | 更新调度/成员信息 | 不改变已记个人消耗 |
| 确认 Codex 全体非正常重置 | 为相关母账号建立新基线 | 重置对应范围用户的 Codex 个人额度 |

事件应包含唯一事件标识、生效时间、影响的平台/额度池、当时的账号成员、每个账号的前后证据、检测置信度、确认来源及处理结果。全体范围应是明确的 Codex 业务账号池，不能把无关 OpenAI API 账号、影子账号都算作独立成员。

自动确认需要检测“变化”，并证明发生在预期正常换期之外，例如多账号可靠用量回落/窗口变化及上游事件信号的交叉验证。时间容差、最少观察次数应由真实样本校准，不直接把现有 ±5 分钟窗口漂移容差当成事件判据。读数缺失/账号离线时不能从分母排除后声称“全部”。

只有一个账号时：可以检测该账号异常，但无法由此证明平台整体事件；应支持管理员确认全体重置，或接入可信上游全局事件。普通用卡流程可以提供“本账号用卡”的强证据，不能触发全体恢复。

建议确认事件在 T 生效后，受影响用户建立新 Codex 周期 `[T, T+7天)`，满额恢复且不累积旧剩余额度，随后继续每 7 天更新；Grok/API 实验不受影响。这是推荐规则，用户尚未明确选择“重置后保留原周锚点”还是“从 T 重新计七天”。两种规则不能在实现中混用。

如果上游没有提供准确事件时间，只能知道发生在两次观察之间，不能把发现时间包装成精确发生时间。应支持确认生效时间，区间内无法归属的消耗保留待处理。

实现可用“平台重置代次 + 个人周期版本”延迟切换，避免重置时同步更新全体用户；但请求鉴权、入账、读接口必须都识别代次，且不能把事件之后新开通用户的额度再次重置。事件唯一约束防止多实例、重启或重复确认导致反复赠送额度。

## 持久化与服务改动范围

以下为逻辑数据模型，表名/字段与迁移 SQL 在实现时细化：

| 数据职责 | 必要信息与约束 |
| --- | --- |
| 额度规则 | purpose、unit、limit、period、anchor policy；Codex 50/Grok 30/实验 500 为默认，实际后台配置有明确优先级 |
| 个人周期与余额汇总 | 用户、用途、period_id、起止时间、重置代次、已结算/暂估/预占用量、版本；用户/用途/周期唯一 |
| 消耗与调整明细 | 请求/尝试、用户周期、真实母账号、额度桶、来源区间、点数或元、状态、校准版本；重复投递不得重复入账 |
| 母账号观察与结算游标 | 观察标识、真实观察时间、窗口标识、官方百分比、来源、已处理区间；进程重启不丢基线 |
| 全体异常重置事件 | 事件标识、证据、影响成员与用户范围、生效时间、确认状态、代次 |

金额和点数分别标明单位，采用数据库 NUMERIC 和一致的十进制舍入，时间采用带时区瞬间。按用户/用途/周期及母账号/窗口/观察时间建立查询索引，不以每个请求扫描全部历史日志实现额度判断。

明细、汇总、幂等标记与周期版本在短事务中一致更新；并发换期/重置/入账通过原子条件更新或行锁解决，不依赖单进程 mutex。网络探测放在事务外。可复用 `UsageBillingRepository.Apply` 的事务/去重思路，但现有 request 级去重不能代替增量对账的区间/调整级去重。

官方观察及待结算任务需要可重放的持久化入口，不能仅依赖 best-effort 日志或内存队列。暂估转正式用差额调整，不能再完整扣一次；晚到补账只影响所属旧周期。纠错可以有显式调整，不能再因其他用户新请求而无记录地回写历史消耗。

## API 实验、倒计时与并发

API 实验继续固定人民币预算，不转成官方点数。GlobalAI 的 `quota/500000` 换算可保留，但上游日志缺失应为待对账，后续按请求幂等补账，不能最终永久记零。其他上游需要明确价格来源、币种/汇率与计价版本；“固定预算”不等于“每次请求固定单价”。

建议额度响应包含 `unit`、`limit`、`used`、`pending`、`remaining`、`blocked`、`period_start`、`resets_at`、`server_now`、`reset_reason`、`data_status`、`updated_at`，具体精度按角色裁剪。未知/暂估不伪装成真实零值。

前端按服务端时间计算倒计时，到点先显示待确认并刷新；不能自己宣布账本已经清零。刷新失败保留旧值但显示过期状态。`49.8/50` 显示100%不等于真实耗尽；零上限应明确禁用。页面恢复可见时重新校时。

如需控制并发超额，应为个人周期增加原子预占，开始请求预占、完成结算、失败释放；未知最终 token 消耗只能预估，单靠预占也不能承诺绝对不超额。应有单请求上限、每用户并发上限和预占超时回收，明确已开始流式请求的处理规则。暂缺新读数不能抹掉已经确认耗尽的账本。

计量/对账在后台按账号合并处理；鉴权只读取或原子检查个人周期汇总，不调用官方探针，也不逐个扫描母账号日志。这同时改善额度正确性和请求响应速度。

## 迁移顺序与验收

1. 固定业务口径：按本文已确认要求建立规则；待定部分采用显式推荐值，落实上线配置。Grok 30 除改默认外，还要识别已存的80配置，区分旧默认与管理员自定义，记录迁移决定，不能仅改代码后声称线上生效。
2. 先建个人周期、明细及后台计量链路，以影子模式验证；个人周期到期、单账号换期、全体重置分别测试。后台规则与旧文档同步更新，避免80/30、元/点双重来源。
3. 定义切换时刻及基线。历史若缺少有效相邻读数，不能声称能精确回填逐请求点数；可明确标记估算迁移余额，或公告一次额度刷新后从新基线起记。不得在无说明情况下重复扣费或丢掉已用量。
4. 使学员卡、管理员个人用量和鉴权同时读取新账本，补齐前端状态；最后移除旧权威查询。回滚要保留新期间消耗，不能直接回到已经不累计的旧元钱包。

最低验收用例：

- 两个用户分别具有不同周起点，各自第7天精确换期；长期不访问也不漂移。
- 同一用户轮换多个母账号仍只有50/30一份上限，旧消耗不因账号删除/离线消失。
- 同一账号多人并发，区间点数守恒，不因个人倍率不同而改变消耗。
- 普通换期/单账号用卡不恢复用户额度；确认全体异常事件只恢复Codex一次。
- 单账号、部分账号无读数、账号成员变化、事件延迟确认、多进程重启不误判全体。
- 跨用户周期、跨官方窗口、跨全体事件的在途请求和晚到读数不串账；重试/重复任务不重扣。
- 有舍入但暂不变的读数、首次无基线、站外消耗、混合用途和错误额度桶不会被当成免费或精确计量。
- API 自然月边界、零上限、上游日志延迟补账；Grok默认30且已存配置迁移正确。
- 99.6%舍入100%仍按真实状态展示，刷新失败/到期不会继续承诺可调用。
- 并发原子预占、异常释放、对账调整与周期切换的一致性；鉴权性能与数据库查询量对照。
