# 开发到部署效率优化：第一阶段

日期：2026-11-13（北京时间）。依据：[调研报告](DELIVERY-EFFICIENCY-RESEARCH-2026-11-13.md)。使用说明：[交付工具](../../tools/DELIVERY.md)。

本轮实现交付工具和测试稳定性改进，没有修改生产业务源码、前端页面或迁移，没有合并上游，没有切换线上程序、重启线上服务或修改生产数据库。根目录用户原有未跟踪文件保留，既有 worktree 残留及历史备份未清理。

## 已落地

- `tools/delivery.py` 提供 validate、review-artifact、quota、build-backend、package、summary 入口。完整前端验证按“浏览器快验 → 最多两项并行的 lint/全量测试/类型 → 一次 Vite 构建”执行；i18n 由全量测试覆盖，常规 `pnpm build` 完整入口保留。
- `delivery_core.py` 记录命令、输入内容、环境摘要、工具版本、起止时间、退出码、日志及产物哈希。只复用匹配的成功证据，变化、损坏、失败及执行中编辑均会失效；超时结束自有子进程树，防止失败命令继续写产物。
- 指纹扫描在遍历前排除 node_modules 等依赖目录，显式依赖元数据仍参与校验；单次 frontend/tools 指纹实测约 0.68 秒。类型编译产生的 vite.config.js/.d.ts、tsbuildinfo 不当成源码变化，Vite 明确使用源 vite.config.ts。
- 浏览器脚本和接口 fixtures 进入版本管理，站点及输出目录参数化。业务写请求和推理被阻止；检查导航、历史、深链接、重复点击、刷新、焦点、复制及三种宽度。等待滚动稳定，短尾部章节按标题可见验收；WebKit 新文档深链接/刷新单独使用最多 15 秒的 load 等待，以完成原生 hash 恢复。
- 公开资源验证共享总时间预算，最多四个并发请求，仅瞬时错误有限重试。哈希不符、缺失资源及业务断言不靠重试放行，原失败证据保留。
- 不可变发布包绑定提交、程序、前端资源和全部验证证据；默认差量包且本地重建验证，完整 gzip 必须显式选择。构建前要求应用输入已提交，未跟踪文件不能悄悄进入程序；只有应用源码未变的文档跟进提交可沿用原运行时 SHA。
- 服务器工具默认预检；校验 payload/基线、备份并验证 dump 后才停应用和原子替换。检查运行容器与有效 Compose 配置是否漂移，正常重建和回退均使用核对过的冻结配置；健康已通过后的持久数据核对失败同样回退程序，始终保留当前数据库。
- 后端生产文件及迁移变化不走这条前端发布通道；已提交的 `_test.go` 变化仍执行真实测试，不当作生产后端变化。原始账本、重置/扩容/纠正审计、钱包起点及持久任务继续受保护，Codex/Grok 不自动转 enforce。
- AGENTS.md 增加流程入口及验证分级约定；CI 增加独立 delivery-tools 任务，包含真实临时 PostgreSQL 验证。

## 实测校准

同一源码、同一机器、同一验证入口连续执行，两轮均实际执行 frozen install 和 Chromium 快验：

| 最终冻结版本 | 完整验证 | 相同输入复跑 |
| --- | ---: | ---: |
| 总耗时 | 303.43 秒 | 34.91 秒 |
| lint | 121.419 秒 | 复用 |
| 类型检查 | 81.912 秒 | 复用 |
| 全量前端测试 | 225.684 秒 | 复用 |
| 前端构建 | 40.807 秒 | 复用 |
| 浏览器快验 | 31.811 秒 | 30.581 秒，实际执行 |

检查并行运行，分项耗时不能相加作为总耗时。另一组较早校准为 293.72 秒 → 31.37 秒。最终相同输入复跑约减少 88.5% 的验证入口耗时；这不代表修改源码后的完整验证也只需 35 秒，更不代表整个需求到线上交付已经达到固定时限。

15–25 分钟继续作为范围清晰、热缓存小修改的候选目标，需要后续真实交付样本校准。源码改变时相关检查仍实际执行。

## 审阅与测试稳定性修正

执行一次独立、只读的全分支审阅，发现 5 个 Important、0 Critical、0 Minor。分别修正并保留失败再通过的证据：生成文件误判输入编辑；未跟踪后端/迁移绕过分级；构建提交与程序来源不一致；Compose 漂移在回退后继续生效；可预测重建临时文件截断硬链接。

最终串联另外捕获两个既有测试假设：Windows 与容器时钟实测约有 31ms 偏差，导致数据库 NOW() 建立的队列截止时间与主机 time.Now() 比较不稳定；WebKit 的新文档原生 hash 恢复晚于 DOMContentLoaded，且尾部短章节不能按固定像素位置验收。前者仅在 `coding_quota_ledger_db_test.go` 改用数据库自身参考时间，保留原扣点、周期和幂等断言；后者调整浏览器等待和可见性断言，未修改指南页面。最终全部必需验证通过，早期失败及被输入变化拒绝的结果不当作有效发布证据。

## 实施取舍和使用边界

- 在用户指定分支原地实施，仅按文件名提交本轮文件；并发编辑由输入指纹检测。实际发布构建需要干净 checkout；当前根目录原有未跟踪文件不能为了过门禁而删除或擅自提交。
- 保留嵌入式前端和常规完整 build，不实施前端独立发布。验证入口协调已有检查；后端生产/迁移升级继续走完整 runbook，没有额度测试豁免。
- 指纹信任 frozen 安装后的依赖内容，校验锁文件、元数据及工具版本；本地证据不是签名系统，不能防御有意伪造 manifest 或依赖存储的行为。
- 最后昂贵的完整验证放在独立审阅和修正后执行，避免审阅修正后立即再做无理由的重复构建；最终证据按当前输入重新核实。
- 本轮没有真实线上程序切换；服务器发布的失败路径在本机受控环境验证，第一次实际使用仍须按说明执行预检、业务数据核对及公开验证。
- 不承诺固定总交付时间；命令复用、真实开发时间、网络、传输和生产切换须分别计时。
