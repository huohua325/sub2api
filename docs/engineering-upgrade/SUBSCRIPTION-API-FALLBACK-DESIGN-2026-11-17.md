## 本轮收敛建议：先做可控的订阅中断接管

以下均是待讨论的产品设计，不是本轮已经启用的策略。目标是订阅过期、耗尽或明确认证失效时，
允许经过授权的请求短期走 API；它不解决网站进程、数据库或服务器本身故障。

### 用户体验与管理员操作

用户沿用原 MILE Key、Base URL 和模型名，不增加客户端开关。正常时仍用订阅；满足条件时
服务端接管，用户在用量明细看到“订阅”或“API 备用”，两者扣同一个用途的周额度。
不能保证每个旧会话都能自动续接：无法安全迁移时明确提示新开会话，不删除历史重试。

管理员在网站中完成：

1. 添加 API Key 账号，配置供应商地址，指定它在某分组／型号下为“备用”；仅添加账号不产生付费资格。
2. 查看型号和能力验证结果，批准对应价卡、用户扣点换算率以及供应商结算倍率。
3. 设置明确的启用到期时间、单请求上限、日支出及本次试用总预算。日预算建议按北京时间自然日，
   试用总预算不因跨日、订阅恢复、开关重开或程序重启而重置；具体金额须另行批准。
4. 先对管理员启用，查看只读决策预览；明确发起小额真实验收后，再授权指定测试用户。
5. 页面显示每个主账号的失效证据、备用触发原因、已结算／预留／待核实费用和恢复订阅情况。
   一键关闭阻止新付费请求，进行中的请求仍完成交接与结算。

建议先在现有统一编程管理员入口验收 GPT 同型号兜底；Grok 使用独立策略和开关，能力验收后
分别开放，不要求两者同批启用。普通独立 Codex/Grok 分组首轮保持现状；以后可显式绑定相同
备用策略，继续保留原 Key 和分组，不把旧分组转换成统一编程。已有统一编程授权不能替代备用授权。

### 请求决策必须回答的四个问题

| 问题 | 准入要求 |
| --- | --- |
| 是否有资格使用备用？ | 用户、分组、平台／型号、协议范围全部获准，策略尚在有效期内 |
| 为什么不用订阅？ | 明确配置的主池非空；所有适用主身份均有有效的过期、耗尽或认证失效证据 |
| 能否保持本次请求语义？ | 同实际型号、同已验证能力，且会话可重建；不能静默降档或删历史 |
| 本次最多花多少？ | 价卡与换算率已批准，输入／输出费用有可落实的上界，个人和运营预算原子预留成功 |

主账号“取消续费”但尚未到期，不算订阅失效；OAuth access token 到期须先走正常刷新。
状态过期或未知时先核实，不能借“没有可调度账号”直接放行 API。
备用策略必须在 previous_response、session sticky 和普通负载均衡之前约束候选；
已有付费会话绑定不能绕过订阅恢复检查。每个请求临发送前再次检查策略与主池证据。
恢复核实复用有界后台刷新／现有健康机制，不为每次正常请求新增同步上游探测。

当前上游 `SubscriptionPriority` 仍在订阅池未选中后尝试常规池（见
`backend/internal/service/openai_account_scheduler.go` 的 `selectByLoadBalance` 分池逻辑），
统一编程 `prepareCodingRequest` 仍要求 OAuth。因此现有开关与账号优先级不能替代上述规则。

### 扣点与支出分开看

以 GPT 待讨论候选 `k=0.13` 演示：某请求官方报价 1 USD，供应商按 0.3 倍结算，
则预计供应商费用为 0.30 名义 USD，用户扣 0.13 点；若其 Codex 上限仍为 50 点，
网站增加 0.26 个百分点。Grok 候选 `k=0.05` 对应官方报价 1 USD、0.25 名义 USD 采购费用、
0.05 点；以 30 点上限计算，增加约 0.1667 个百分点。采购折扣不能在用户扣点公式里重复乘一次。

这两个 k 是上周工作量的粗略试验候选，尚未批准；GPT 单型号差异与 Grok 日波动见下文样本。
初版可先采用每用途固定 k；如果要求 GPT-6.1 Sol 等各型号更接近原订阅体验，应在启用前
选定逐型号版本，缺少可靠样本的型号继续关闭。采购倍率、现金币种和充值汇率独立核实，
不能把供应商界面“美元余额”直接当现金支出。

同一请求只结算一次编程点数，不能再经普通 API 计费分支重复扣用户美元钱包；既有 Key 限额
继续生效。付费新增请求对个人剩余额度和运营预算都执行预留检查，订阅的 shadow 模式不变。
个人可用余额不明、预算或计费存储不可用时，拒绝新增付费，保留原订阅路径的既有行为。

上游新引入的 Ultra Fast／服务档位也须纳入能力和价卡冻结。首轮不自动打开 Ultra Fast，
不把未知 `service_tier` 按标准价格放行；经批准的标准档须按供应商可验证的语义发送。
已有按字节估 token 的订阅估算不能直接当付费硬预算保证，必须验证其上界或另定保守边界。

### 最小交付与停止条件

按三个可审查交付推进：先做不发送付费请求的策略预览及原因测试；再完成有界成本、持久预算、
固定扣点和恢复器，用模拟上游及真实隔离 PostgreSQL 验收；最后才进行管理员小额真实调用。
预览中的“如果走 API 会怎样”只作观察，不设置全局 enforce，也不代表允许付费。

首版只承诺经验证的 HTTP Responses、文本和代码工具流。供应商同样使用 sub2api 并不能证明
其实际模型、原生 Responses、工具续接及 usage 都兼容，仍须按具体端点验收。
如果供应商缺等价型号、会话依赖不可移植状态、无法界定成本或缺少可信 usage，
对应范围不启用自动备用；不为追求“无感”吞掉这些限制。

实施前只需补齐三组业务输入：供应商地址及可用型号／能力；选定的扣点率与结算口径；
已批准的管理员试用预算／有效期。实际 Key 只通过账号管理或本机受保护入口提供，不写入本文。
本轮只更新设计文档，不连接生产、不调用模型、不更改配置或历史账本。

## 目标与第一版范围

保留现有 MILE Key、Base URL、milelab Provider、auth.json 和客户端历史。
由服务端区分订阅主池和明确授权的 API Key 备用池，针对请求实际目标平台及具体型号决策。
不通过把 Key 换到 API 实验分组实现备用，不静默更换模型。

第一版只覆盖统一编程的 HTTP Responses 文本、已验证的工具调用及其流式响应。
OpenAI 和 Grok 分别接入、分别验收；实际没有等价 API 型号时，该型号不能标为可兜底。
图片、远程压缩及复杂工具扩展只有通过对应能力验收后才获得备用资格。
WebSocket、实时音视频、后台异步任务先不纳入。复用现有 Go、PostgreSQL、Redis，
不增加 CLIProxyAPI 等独立常驻服务。

## 当前实现不能直接满足的地方

| 现有机制 | 限制 |
| --- | --- |
| OpenAI 高级调度的订阅优先 | 订阅池拿不到并发席位就可能尝试非订阅池；Grok 不属于其 ChatGPT 订阅分类 |
| previous_response/session sticky | 在分池之前命中，旧付费绑定可能一直优先于已恢复的订阅 |

## 调度策略：默认严格备用

主池和备用池是当前分组、平台、型号下明确配置的角色，备用默认空、默认关闭。
不是把全站所有 API Key 都当作候选；同一个账号在其他分组的角色不带来本组的付费许可。
主池配置为空、账号被全部解绑或读取失败，均不能推导出付费许可。
同母账号的多个 shadow 只算同一个上游身份。

| 情况 | 第一版默认处理 |
| --- | --- |
| 存在健康订阅账号 | 使用订阅；不调用备用 |
| 订阅账号并发满、队列满或本地排队超时 | 排队或返回繁忙，不转付费 |
| 某个订阅账号过期、官方确认额度耗尽 | 尝试其他合格主账号；全部明确失效后才允许备用 |
| OAuth token 到期 | 先刷新；网络刷新失败不是订阅到期证据，明确认证失效才可进入失效判定 |
| 短期限流或普通 429 | 尊重 Retry-After、换主账号，不默认付费；明确额度语义的 429 另按耗尽处理 |
| 401/403 | 先分类；仅确认的认证/订阅问题可计为主池失效，内容政策拒绝不能通过备用绕过 |
| 5xx、连接错误、响应超时 | 有界主池重试；第一版不默认因此付费，后续可另设有时限的故障策略 |
| 用户自己额度耗尽、Key 配额用完或未获授权 | 继续拦截，备用不能绕过 |
| 主池因模型/能力不支持而无候选 | 不自动变成 API 常规调用；新增仅 API 可用型号需单独明确开放 |
| 主池状态未知、数据库/缓存/配置异常、管理员暂停 | 不自动付费 |

因此第一版优先解决“订阅过期或耗尽期间继续服务”，不宣称覆盖所有网络/平台故障。
主账号不可用证据应含原因、来源、发生时间、适用型号及有效期，不能只依赖
`IsSchedulable=false`、本请求的 ExcludedIDs 或内存中的单次失败。

建议请求顺序：鉴权及原个人额度 → 主池状态与请求兼容判定 → 主池正常选号 →
若全部明确失效，核对备用授权、价卡、倍率和预算 → 原子预留 → 发送前再核对策略版本及资格 →
发送一次上游尝试 → 持久交接计费。

订阅恢复后，可安全迁移的新请求重新优先订阅。语义是“付费决策时主池不可用”，
不能保证主账号下一毫秒恢复时已获准发送的 API 请求立即取消。

## 会话和模型兼容

同一个公开模型名必须映射到经过验证的等价实际型号；供应商的 `/models` 列表和一次简单回答
不能证明代码工具、推理档位、长上下文和压缩都兼容。只有 Chat Completions 的供应商，
不能在未经协议及工具验收时加入 Responses 备用池。

先保持主池的现有模型目录。备用账号单独参与兼容验证和本次请求的能力检查，
避免仅新增备用成员就降低主池对所有用户宣告的能力。
管理员查看逐项能力矩阵：原生 Responses、SSE、实际型号、上下文、推理档位、
function/custom/namespace 工具、图片及 compact。只为通过的范围授予备用资格。

自动切换只允许新会话，或能够证明当前请求已包含完整所需历史的情况。
工具输出必须有对应调用；previous_response_id、encrypted reasoning、compaction blob
不能默认跨账号/供应商使用，也不能通过删除关键历史来声称续接成功。
无法完整重建时明确返回“此会话无法自动转备用，请新开会话”，保留原会话。

已发送但结果未知的尝试不默认重放到付费池；已产生有效文本或工具调用后不切池拼接输出。
同一逻辑请求共享总 deadline 和重试次数，换池不重新获得一套重试额度。
严格模式下，不允许付费 sticky 绕过已恢复的主池；若用户以后希望状态绑定会话继续在 API
运行到结束，应另行授权这个有费用上限和时限的例外。

## 扣点：同一周钱包，独立费用证据

按用户选择采用：

```text
API 本次扣点 = 已审核 API 价卡计算的 USD 金额 × 对应用途的 points_per_USD
个人本周已用 = 既有订阅扣点投影 + API 固定扣点 + 原有待结算用量
准入另外考虑在途预留及尚未核实的占用；学生展示沿用现有百分比语义。
```

Codex/Grok 分别配置倍率，不混扣。原个人上限和 168 小时周期、钱包起点不变；
调用开始后才完成的请求仍归属原开始时间对应的周期，不以结算或重试时间换周。
API 实验月钱包不受影响，不新增用户应急钱包。

### 金额基准与倍率

新增独立的 API 费用基准：供应商、最终转发模型、已审核价卡版本、完整 usage、
缓存及输出/推理计价、允许的服务档位和额外收费项目。第一版仅支持明确的 USD 价卡。
该金额是“按已审核合同价计算的费用”，不是自动取得的供应商发票实付。
可信的逐请求上游扣费证据另存，发生差异通过追加对账修正，不覆盖历史。

不直接使用已有 TotalCost、ActualCost、AccountStatsCost，亦不使用调度的 UpstreamCost 因子。
分组打折、赠送倍率或客户售价归零，不能让实际付费 API 的编程扣点变成零。
免费缓存/免费项目必须有明确价卡证据，缺少定价不是免费。

倍率保存不可改写的版本、批准人和生效时间。发送前冻结价卡与倍率版本；
之后修改倍率不重算旧请求，待结算任务和重启恢复仍读取原版本。
第一版推荐管理员显式设定固定倍率。后续可以从可信订阅样本和同口径 API 等价费用生成
建议值，但不自动批准，不拿订阅月费直接除成点价，不实时跟随过期校准。
没有可信样本时不给出伪精确建议值。

例如“2 点/USD，费用 0.10 USD → 0.20 点”只用于说明公式，不是推荐上线倍率。
界面应预览典型请求扣点，以及当前个人额度大致对应多少 API 计价金额。

### 依据历史工作量确定换算率（11 月 17 日补充）

供应商折扣是采购成本参数，不应直接乘在原有用户点数上。目标是同一批工作量在订阅和
API 备用下扣除近似相同的编程点数，不能因采购更便宜而自动扩大个人权益。

```text
B = 同一批历史请求按已确认官方价卡重报价的金额（USD 计价单位）
P = 同批已结算真实请求在统一容量口径下的编程点数（含审计纠正）
k = P / B                         # 每官方价 USD 对应多少编程点

GPT 预计采购成本 = B × 0.3
Grok 预计采购成本 = B × 0.25
API 新请求用户扣点 = 该请求官方价金额 × k

若仍以采购成本为输入：
GPT 每采购 USD 扣点倍率 = k / 0.3
Grok 每采购 USD 扣点倍率 = k / 0.25
```

上述两种计算在同一价卡和采购倍率版本下等价。建议管理端主要配置官方价换算率 k，
采购倍率单独显示，派生采购金额扣点率，避免采购折扣变化后忘记同步换算率。
倍率和价卡按 Codex/Grok 分别保存，不混合推算；现金充值折扣、货币汇率与价卡单位也需区分。

初次校准取北京时间 2026-11-09 00:00 至 2026-11-16 00:00 的完整自然周，
再以滚动七天和按日/型号分组比较稳定性。主建议只用已结算、非导入、可与 usage_logs 唯一
匹配的真实请求；账本和费用分母必须来自同一批样本，并报告缺日志、未结算及无法报价的覆盖率。
按 `(request_id, api_key_id)` 匹配，存在重复日志的请求单独核查，不放大连接结果。

点数先合入审计纠正，再按已确认容量事件投影到同一参考口径；个人重置是额外授信，
不会减少实际工作量，不能用其豁免后的点数校准 k。实际个人展示则继续执行现有重置规则。
不把学生显示百分比当作点数，不用代码默认值猜测当前个人上限。

按实际模型、缓存输入、普通输入、输出、服务档、长上下文和额外费用分别重报价。
现有 GPT 日志的普通输入桶已排除缓存读写，不能再减一次缓存。
同时估算沿用历史缓存命中与备用冷缓存两种费用；同样会话在切换后可能失去缓存，

### 持久账本隔离

原订阅历史不回填、不重写。API 固定扣点不参与订阅 meter 校准、官方百分比观察、
母账号容量折算或全体异常重置的检测，不把 API 账号伪装成订阅母账号。

个人额度读取、鉴权和管理员用量监控必须使用同一合并视图；按来源分别展示，不能在母账号

## 支出限制、并发与恢复

额外设全站/分组/账号的付费费用上限，作为运营成本限制；它们不增加个人权益或新周钱包。
在已有个人额度和 Key 配额检查之外，付费发送必须取得持久、原子的支出许可。
原订阅 Codex/Grok 的 shadow 模式保持不变；新的付费支出门禁独立、默认关闭，
启用后不能因订阅处于 shadow 而忽略运营预算。

同一 PostgreSQL 事务协调个人剩余点数及所有适用预算，固定顺序锁定，跨 Key 共享；
使用已结算、在途预留、未知占用判断是否还能发送。不仅依靠 Redis 或完成后的累计费用。
使用 decimal/numeric，不用浮点金额；按项目 PostgreSQL 约定设计约束和唯一键。

预留必须有可信的输入成本边界、服务端落实的输出上限和完整价卡。无法界定额外工具费用、
输入成本或输出上限的请求，第一版拒绝自动付费。预算只能在这些假设成立时约束本地准入，
不能宣称远端供应商账单绝无超支；还应配置供应商侧余额/硬限额。

逻辑请求 ID 与每次上游尝试 ID 分开：共享个人协调和总重试预算，同时保留每次真实发送及
其成本。业务内部重放不能重复扣同一尝试，也不能因换账号覆盖此前已经发生的消耗。
跨服务网络不能保证上游绝对只执行一次，未知结果不能当成零费用自动再发。

未发送的预留可释放；已发送但超时、断流、缺 usage 或进程中断的记录保持待核实和预算占用，
不因 TTL、重启或用户取消归零。已知部分用量按证据结算，后续差异追加纠正。
后台重放只执行持久计费，不再次调用模型。

复用现有 reservation、billing_tasks、async_jobs 和交接/恢复框架，但须版本化扩展命令；
保留旧命令 fingerprint 的解释规则，不能使升级前的待处理任务变成冲突或被忽略。
新来源必须显式排除在订阅重估 SQL 之外，不能只指望“正常不会收到该账号观察”。

## 管理、灰度与回退

管理员配置每个型号的主/备用账号、允许原因、价卡、倍率和付费总限额。
显示备用状态（关闭、未验证、就绪、预算不足、会话不兼容）、当前主池状态、
最近触发原因、付费量和失败/待核实记录。真实付费能力探测应是明确动作，并展示费用证据，
配置保存不能偷偷发起推理测试。

默认只允许管理员；之后在现有统一编程权限范围内显式授权指定测试用户。
原本已获订阅组权限不等于自动获得付费备用权限。目录、Key 绑定、实际调用都执行后端授权。
普通分组、原 Key 绑定、用户客户端文件、原权限名单不自动改变。

使用独立的新增兼容迁移和持久策略/费用证据/预算状态，既有迁移保持原样。
关停只阻止新的付费准入，仍需结算已发送请求并恢复旧任务。
含有 API 扣点或待处理新命令后，不能回退到不认识它们的旧程序。
优先关闭入口并保留兼容恢复器向前修复，不恢复旧数据库覆盖新消耗。

## 验收与分步交付

1. 先实现/审查决定原因和只读模拟：健康、忙碌、空主池、短期 429、未知状态均不付费。
2. 用模拟原生 Responses 上游验证同型号多轮工具、流式、能力拒绝、恢复和会话迁移边界。
3. 用真实隔离 PostgreSQL `-race` 验证跨 Key 并发预算、重复回执、改倍率后重放、断电恢复、
   跨周期、官方事件、容量折算、个人重置、原账本不变；不能把 skip 记为通过。
4. 管理员用很小的已批准预算对真实备用端点验收 CLI 和 VSCode；只对通过的型号/能力开放。
5. 显式授权少量测试用户，核对自动接管、恢复订阅、费用、点数和待核实记录后，再决定公开。

必须包含：主池健康时备用调用数为零；主池一坏一好时只走好的订阅；所有明确失效才接管；
忙碌不付费；内容拒绝不绕过；额度耗尽不旁路；已输出不跨池重放；不明消耗不退款；
未批准倍率/价卡不发送；修改倍率不影响旧结算；API 点数不受订阅重估/扩容污染；
恢复器和原影子模式不受升级/关停破坏；备用未启用时原客户端目录不变。

这是调度、计量和兼容性共同改动，不按纯前端或普通账号配置发布。
复用交付工具，先实际用户路径再最终冻结/验证/一次构建；后端发布通道需新增明确契约，
不能借用现有仅支持特定历史版本的发布通道绕过检查。
